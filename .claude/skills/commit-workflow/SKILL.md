# 提交流程

每次 `git commit`，husky 的 `commit-msg` 钩子用 commitlint 检查提交信息，不符合 Conventional Commits（`type(scope): subject`）就拦下；`pre-commit` 钩子用 lint-staged 对暂存的文件跑 `scripts/format.sh`。根 `package.json` 的 `"prepare": "husky"` 让钩子在 `pnpm install` 后自动生效。三个包都是不发布的应用，所以没有 changesets，提交信息只影响历史好不好读，不决定版本号。

日常提交用 `/commit`（只提交已暂存的改动）或 `/split-commits`（把一堆改动拆成多个提交）。type 和 scope 的约定写在 CLAUDE.md「Git 提交约定」。

## 钩子出问题时

| 现象                                                                  | 处理                                                                                                                              |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 提交被 commitlint 拦下                                                | 按报错改提交信息。**不要用 `--no-verify` 绕过**                                                                                   |
| 钩子没跑，或者报找不到 commitlint / lint-staged                       | 先 `pnpm install`：它会跑 `prepare: husky` 激活钩子；钩子靠 `pnpm exec`，没装依赖时提交会失败                                     |
| CI 里用 `--ignore-scripts` 等方式安装时 `prepare` 报错                | 设 `HUSKY=0`                                                                                                                      |
| pre-commit 开头打印 "might result in data loss"                       | 可以忽略，原因见 [lint-format 的 tech.md §9](../lint-format/references/tech.md#9-pre-commit-钩子2026-10-22)                       |
| pre-commit 报 `Failed to restore unstaged changes!`，文件里有冲突标记 | 没暂存的改动和被格式化的改动落在同一行。手动解决冲突；没暂存的改动在 `.git/lint-staged/<runId>/unstaged.patch` 里还有一份，不会丢 |

## 改提交规范或钩子

- commitlint 规则改根目录的 `commitlint.config.js`（现在只有 `extends: ['@commitlint/config-conventional']`）。改完各试一条合规和不合规的：`echo "feat(server): add x" | pnpm exec commitlint` 退出码 0，`echo "bad" | pnpm exec commitlint` 退出码 1。
- 钩子在 `.husky/`：`commit-msg` 是 `pnpm exec commitlint --edit "$1"`，`pre-commit` 是 `pnpm exec lint-staged --no-stash`。husky、commitlint、lint-staged 只装在根目录（`pnpm add -Dw`），不装进子包。
- pre-commit 只修复和格式化，不跑测试、不拦 lint 错误。当初删掉 `husky init` 生成的 `pnpm test` 钩子，就是因为每次提交跑全量测试太重。要往里加检查，先量一下提交会慢多少。pre-commit 的细节归 `lint-format` skill 管。
- type / scope 的约定变了，同时改 CLAUDE.md「Git 提交约定」和 `.claude/commands/commit.md`。
- 改完在 [references/plan.md](references/plan.md) 加一个日期小节，[references/tech.md](references/tech.md) 和 [references/verification.md](references/verification.md) 里变了的地方一起改，写法按 `feature-docs` skill。

## 以后要发版时

在 `packages/*` 放了要发布到 registry 的包时，再评估要不要引入 changesets。迁移路径：装 `@changesets/cli` → `changeset init` → 补 `/release` 命令 →（发私有 registry 时）配 `access: "restricted"` 和登录态。现在的 Conventional Commits 历史可以直接当基础。理由和代价见 [tech.md §1](references/tech.md#1-选型2026-07-19)、[§4](references/tech.md#4-以后要发版时2026-07-19)。

## 关键决定

- 只做"提交工作流"，不引入 changesets、不建 `/release`：没有要发布的包（用户在两个选项里选的，2026-07-19，见 [tech.md §1](references/tech.md#1-选型2026-07-19)）
- 装 commitlint + husky 做机器兜底（用户选择安装，见 [tech.md §2](references/tech.md#2-钩子与配置2026-07-192026-10-22-修订)）
- 删掉 `husky init` 生成的 `pnpm test` pre-commit 钩子：每次提交跑全量测试太重。2026-10-22 加回的 pre-commit 只格式化暂存文件，不跑测试（见 [tech.md §2](references/tech.md#2-钩子与配置2026-07-192026-10-22-修订)、`lint-format` skill）
- 提交信息不加 "Generated by Claude"、co-author 之类的尾注，不用 `--no-verify` 绕过钩子（见 CLAUDE.md「Git 提交约定」和 [tech.md §3](references/tech.md#3-slash-command2026-07-19)）
